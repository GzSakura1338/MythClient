# AutoCharge 设计

## 目标玩家上方（Target Player）

`Target Player` 默认关闭；右侧小齿轮提供 `FOV`（1–360，默认 180）和 `Range`（1–32 格，默认 16）。
开启后仍是每次触发执行一组珍珠＋风弹，结束自动关闭，不会一直扫描并连续消耗物品。

- 从真实玩家列表中筛选，排除自己、死亡/旁观者、Teams 队友及 AntiBot 对象；按距离选择范围内、摄像机水平 FOV 内最近的一人。
- 没有符合条件的玩家、投掷前目标丢失，或两条目标弹道都无法可靠接珠时，本次自动回退普通向上投掷，使用 Height，不要求再次按键；本次不重新抓取原失败目标。回退后先按原 Rotation Speed 转到向上方向，再检查头顶空间和物品，不能沿失败的目标角度直接投掷。
- 锁定该玩家的实体身份，投出珍珠后不换目标。投掷前再次检查 FOV/Range；投出后继续校验目标身份及存活，不因越过初始 Range 或转动摄像机而取消。
- 按最新要求，此模式只定位目标的 XZ，完全忽略 `Height`：不用于起手角度、候选排序或投掷门槛。关闭目标模式才使用 Height。
- `Targeting.h` 根据原版水平阻力递推反算 XZ 发射速度，补偿自身速度并外推目标水平位置；剩余发射速度分配给向上分量。Y 由物理弹道决定，不追求指定高度或目标头顶的固定 Y。
- 水平预测速度上限为 0.8 格/tick。先平滑到可发射的角度，再检查后续风弹存在可靠拦截窗口。优先短飞行时间的弹道；不通过时检查另一条高抛弹道，仍无解则在使用珍珠前切换普通向上流程。
- 珍珠投出后用实际观测轨迹重算风弹；优先选择目标预测 XZ 水平 2 格内的窗口。没有该窗口时，改选尽可能接近目标 XZ 的可靠接珠角度，避免一直等到珍珠消失。碰撞余量、散布与相位门槛不降低，也没有目标高度误差限制。投掷复验使用共享 RotationManager 的实际发布角度。
- 两发均检查方块和实体遮挡，不改变物理速度；复用静默转头、移动修复、切槽交接及手动右键隔离。已投珠后目标丢失或瞬移时保留最后 XZ、停止外推，继续完成接珠；不重新选人或再投珍珠。

Range 是筛选距离，不是弹道保证。部分远距离组合仍无法同时满足两发拦截及 XZ 位置，即使珍珠单独可达也会回退普通向上流程。随机散布、目标急转、延迟和服务端改动仍可能导致偏差；预测允许区间不是实服落点承诺。

目标求解器验证：48 个目标 Y/距离/自身与目标移动组合中，4/8 格的 32 个组合全部完成名义两发流程；16 格的 16 个组合没有可靠目标联动窗口，不计目标定位成功。生产状态机遇到该情况改走普通向上流程。加入珍珠随机散布后 128/128 次找到风弹窗口，独立碰撞样本为 32,768/32,768 相撞；这是模拟结果，不代表实服成功率。
生产模块回归验证 Height=5/25/45 使用相同发射角度、都完成两发；并覆盖投出后超出 Range 仍继续、FOV、360° 背后目标、队友/Bot/非玩家排除、目标消失、遮挡和恢复。完整日志：`Client/build-vs2026/autocharge-xz-validation.txt`。

## 2026-09-29 当前实现

本节描述本轮重构后的行为；下文早期专项数据保留作为历史记录，当前验收结果见 [autocharge-validation.md](autocharge-validation.md)。

- `Trajectory.h`：统一首次碰撞与轨迹推进，跟踪/候选/投掷复验共用同一离散物理模型；缓存珍珠未来路径，避免每个散布样本重复推进。
- `Prediction.h`：维护发送位移、拟合珍珠年龄、评价高度和散布风险。每个候选使用 128 个名义散布探针，另评估前后 1 tick 各 128 个探针与 26 个散布边界点。投掷门槛是名义漏接至多 1/128、最差相位漏接至多 2/128；边界点仍用于排序。模型置信度不是实服概率。
- `WindPlanner.h`：先将候选变成当前 tick 实际可发布的平滑/量化角度，再计算碰撞和质量；同一 tick 使用固定灵敏度网格，不对每个候选重复随机扰动。最终角度原样交给共享 RotationManager，读取管理器结果后再次检查。
- 上升阶段等待，不先消耗珍珠；落地/不再上升后才提交。第一发垂直向上时预先将静默 yaw 朝向水平移动的反方向，减少第二发补偿时的转头距离。摄像机不变。
- 只有已落地且最近位移稳定，才允许为了更好的高度等待未来窗口。跳跃、转向、急停时不以恒定速度的假设放弃已验证的当前窗口。
- 落地交界额外检查脚底短距离碰撞，以及实际 onGround 与发送位移的矛盾；存在继承 Y 突然归零的可能时暂缓投掷，下一 tick 重算。日志曾出现实际风弹 Y 与预测相差约 0.397，超出散布范围；原版 shootFromRotation 会在 onGround 时将继承 Y 归零。碰撞探测是保守保护，不能证明所有服务器时序完全一致。
- 先确认珍珠实体 ID 再建立遮挡列表，避免将刚识别的自身珍珠当作障碍。候选路径的遮挡参与筛选，不能因几何最优候选被挡就永久忽略其他可用方向。
- `AutoCharge.cpp` 只负责状态机、资源所有权和原生提交。同一 tick 的重复交互回调不会继续消耗转头预算；使用已提交或返回不明时，不重投、也不在该 tick 提前恢复槽位/手动右键。
- AutoMace 工作时不能启动或继续 AutoCharge；AutoMLG 紧急接管仍使用原有交接入口。AutoMace 与 AutoMLG 的既定优先级未反转。

高延迟或持续转向可能错过所有可靠窗口；此时珍珠可能已经投出，但模块不继续浪费风弹。Height 是高度偏好，可靠相撞优先；高于原版珍珠顶点的目标不可保证，低高度也可能因可靠性门槛超出设定值。

## 原版右键隔离

执行期间屏蔽 `Minecraft.startUseItem` 的原版 ClickEvent，并在原版交互处理前
清零 use 绑定的 held 状态和 clickCount。读取实际绑定，支持用户改右键绑定。
模块自己的控制器使用调用不经过这个原版输入入口，仍可正常投珍珠、风弹。
物理右键不再触发 Context 中断；Stop、异常或最后一次使用后继续屏蔽到下一 tick，
再恢复物理按住状态，不回放累积点击。防止原版使用的相机角度混入静默投掷所在 tick。
这对应 Grim BadPacketsJ 的 use-item rotation 与 tick rotation 一致性检查；
测试覆盖了屏蔽跨 Stop 保持和只恢复一次，实际服务端验证由用户完成。

状态：已实现原生 C++/JNI 首版。先朝上投掷末影珍珠，再投掷风弹；通过移动补偿使珍珠碰到风弹，触发珍珠碰撞传送。支持 Lunar 1.21.11 / Minecraft 26.3，实际服务端效果由用户注入验证。

## 行为与边界

- 分类建议为 Player，名称 `AutoCharge`。按绑定键执行一次，结束或失败后自动关闭，避免持续消耗物品。
- 顺序固定为：准备朝向 → 珍珠 → 跟踪珍珠 → 风弹 → 归还朝向和物品栏。
- 按最新要求采用静默转头，摄像机保持用户视角；第一发接近垂直向上，第二发按轨迹倾斜。服务端朝向由共享 RotationManager 发布。
- 不主动中断疾跑，不冻结玩家坐标，不改写速度，不伪造传送。移动修复负责保持用户输入的世界方向，不能保证所有拦截角度都满足原版的向前疾跑条件。
- 最终是否传送、在何时传送，由服务器处理珍珠的实际碰撞决定。核心是珍珠命中可被选中的风弹，不是风弹爆炸推动珍珠；本地投掷成功不显示为已经传送。
- 原版风弹自 1.21 提供。现有 Lunar 1.21.11 / 26.3 是首批候选适配；1.7、1.8、1.20.1 不伪装支持原版不存在的物品。插件物品另外适配。

## 已核对的游戏机制

Recaf 分析 Lunar 1.21.11 bake.zip 与 26.3 客户端后确认：风弹属于可重定向投射物，是珍珠可命中的实体；珍珠本身不属于该标签。珍珠命中后的服务端处理才负责传送。两者发射速度均为 1.5，继承玩家水平速度，空中额外继承垂直速度；珍珠每 tick 先施加 0.03 重力，再乘 float 0.99 阻力，风弹保持发射速度。原版发射含随机散布，不能保证百分之百相撞。

预测以通常较早更新的珍珠扫掠线段，对较晚更新的风弹包围盒进行离散检测，含 ProjectileUtil 的随年龄增长 margin。客户端实体快照不等同服务器当前时刻，网络延迟和实体更新顺序是首版限制。

预判重写：移除 position−xo/yo/zo 的发射速度估算。监听未被取消的出站移动包及 tick-end 包，维护最近发送坐标、实际位移和 onGround；仅转头包使本次位移为零，无移动的 tick 也清零，与已核对的服务端已知运动语义一致。这是客户端观察的发送状态，不伪称服务器确认。发生明显坐标突变时拒绝使用该位移。

记录珍珠实际提交 tick 和发射点（眼位下方 0.1）。对接收到的珍珠位置/速度逆向积分，拟合它已飞行的时间；再按两次 use 请求之间的 tick 间隔推进到第二次发射时刻。不能把实体到达后的本地 tickCount 当作服务端飞行年龄。拟合偏差超过 0.3 格则等待新的可信快照，不直接沿错误轨迹发射。

求解器改为“珍珠扫掠线段与风弹可达球面相交”的二次方程，显式满足 1.5 发射速度，再做灵敏度量化、平滑和碰撞验证。预测窗口扩展到 32 tick，允许等待珍珠减速/下降后的可达窗口。预留随机散布余量；网络抖动、服务端拒收/重写运动和实体先后更新仍可能造成误差。

回归测试包含 144 个延迟快照对齐场景、测量误差、移动包/仅转头包/空 tick/坐标突变，以及跑跳随机散布和延后相遇窗口。上一版的同时间理想轨迹测试遗漏了客户端快照延迟，不能作为实服成功率依据。

核对范围：

1. 珍珠与风弹的初始位置、初速度、是否继承玩家 XYZ 速度、重力和阻力，以及离散 tick 更新顺序。
2. 风弹是否把本玩家刚发射的珍珠视作可碰撞实体；所有者排除、离开所有者判定和命中体积。
3. 风弹碰撞/爆炸是否推动珍珠，推动方向和条件，以及珍珠的碰撞/传送逻辑。
4. 物品冷却、投掷散布、使用方法、交互包是否直接携带角度，以及客户端/服务器分别在哪里创建实体。

如果目标版本的原版机制不支持这一组合，应报告结果，不用修改实体运动或伪造包来替代所需机制。客户端分析也不能证明服务器插件未改动这些行为。

## 状态机

| 状态 | 行为 | 转移条件 |
| --- | --- | --- |
| Validate | 检查版本、存活、世界、快捷栏双物品、冷却、头顶空间和其他模块占用 | 条件满足后才申请资源 |
| AimPearl | 获取独占转头，平滑抬头；接近发射时才申请珍珠槽位 | 实际有效角度和物品同步满足该版本使用条件 |
| ThrowPearl | 在原生交互阶段调用物品使用，一次执行最多发射一颗 | 已提交则进入确认阶段，不因暂未看到实体反复点击 |
| TrackPearl | 根据所有者、本次出生时间、发射点匹配珍珠；记录实体 ID、位置和速度 | 确认自己的珍珠，且预测能形成拦截 |
| AimWind | 每 tick 从当前玩家眼位重算风弹轨迹，平滑跟随拦截方向 | 修正后的有效角度对应可靠命中窗口 |
| ThrowWind | 申请风弹槽位并同步，用原生接口发射一次 | 标记已提交，不重复追发 |
| Restore | 保持必要的交互边界，再平滑回正、归还槽位和转头 | 关闭模块 |
| Abort | 记录简短失败原因，停止后续投掷并释放资源 | 关闭模块 |

停止、切世界、死亡、打开界面、失去独占权、物品被移动/耗尽、冷却阻断、超时、珍珠消失或轨迹被墙阻挡，都进入 Abort。首发之后取消无法撤回已经投出的珍珠。

超时是内部有界限制，不让模块无限占用朝向。实体延迟到达时只等待，不重发第一颗。屏幕帧率不参与阶段计时；角度每游戏 tick 只推进一次。

## 疾跑下的水平补偿

目标不是让两次发射起点 XZ 相等，而是让两条弹道在同一时刻、同一位置发生有效碰撞。

珍珠发射点记作 E0；风弹发射时，玩家已经移动到 E1。求解必须同时考虑 E1−E0、珍珠当前运动和风弹实际继承的玩家速度，不能直接沿第一发的 yaw/pitch 再抛一次。

每 tick 对少量候选发射时机和飞行时长进行有界搜索：

1. 从确认的珍珠位置/速度，按目标版本离散运动方程预测未来位置 P(t)。
2. 从风弹预计发射眼位 E1 与玩家当时速度构建风弹初始状态；只有代码确认会继承的速度分量才能加入。
3. 求使 W(t) 接近 P(t) 的初始方向，转换成 yaw/pitch。
4. 经共享转头管理的连续 yaw、灵敏度量化和平滑步进后，重新模拟实际角度，不能用未经量化的理想解判定命中。
5. 用逐段扫掠碰撞检测检查风弹与移动珍珠的包围盒，避免两者在一个 tick 内交叉却被端点距离漏掉；同时检查方块阻挡和更早的其他实体碰撞。
6. 选最早、误差余量足够的窗口；预留原版散布和观测误差。玩家转向、起跳、受击或加速后立即重算。

如果还没看到可确认的珍珠，只可计算候选预测，不能按一个固定毫秒数盲投风弹。不要把 ping 直接当作固定飞行 tick 数；利用连续实体快照约束估计，不假设能知道服务器的精确当前时刻。

`Height` 是目标高度，按珍珠投出时玩家脚底为 0，范围 5–45 格，步进 0.5 格，默认 25。模块不会把它换算成固定毫秒：每个游戏 tick 根据收到的珍珠位置/速度、玩家实际移动、风弹初速和碰撞体积反算下一次可行的风弹角度与时机。等待实体确认期间继续跟踪，实际角度经过灵敏度量化后会重新验证。

求解检查第一次真实包围盒相交，以碰撞 tick 开始时珍珠的 `oldPosition()` 作为玩家脚底传送目标；不是交点或后续中心穿越。高度用于给可命中的候选排序，不再是投掷的硬门槛。64 个独立三角散布探针至少 62 个必须命中，但不再要求每个随机结果同时落在高度误差带内。实际平滑、量化后的角度仍必须通过碰撞、散布余量和路径检查。

目标在珍珠提交时快照。目标高于预计顶点不再取消珍珠，而是寻找接近目标的可靠拦截。每 tick 最多向前估计 8 tick；只有预计窗口的综合代价至少改善 0.15 时才推迟当前投掷，不能只比较高度。代价包含高度误差、散布漏接、极限散布和相位敏感性。进入目标 ±0.75 格后，只有名义探针无漏接且最差相位最多漏接 2/64 时才直接投掷，否则仍比较更可靠的下一窗口；珍珠发出 24 tick 后不再为改善高度额外等待。这个上限不绕过实体确认、角度和路径检查，不能在没有安全角度时盲投。

未来玩家运动只用于决定是否短暂等待；真正发射必须用当前移动快照重新验证。站立低目标（例如 5 格）可能低于最早确认后能拦截到的高度，高目标也可能超过珍珠顶点；这种情况选择可达高度，不宣称精确达到设置值。不会为了低目标强制等到珍珠下降数秒后，导致移动玩家错过窗口。仍允许跟踪到 110 个飞行 tick，总执行上限 360 tick。

| 相交扩张 | `class_1675.method_71624`：目标风弹盒扩张 `clamp(float(tickCount-2)/20f,0f,0.3f)` |
| 年龄顺序 | `class_3218.method_18762`：先保存旧坐标、增加 tickCount，再执行实体 tick；不采用渲染插值年龄 |
| 传送脚底 | `class_1684.method_7488` 调用 `class_1297.method_61411`：返回 xOld/yOld/zOld；不是射线碰撞点 |

模型限定未被外物改变的空中弹道。珍珠进入水中会拒绝使用该模型；服务器插件、网络 tick 相位、其他实体更新顺序仍可能产生偏差。26.3 继续使用已有共同空气参数适配，本次新核对的证据来自 Lunar。

修复后的验证要求所有空旷基准场景完成第二次投掷，不能把无解后不投当成通过：216/216 个不同世界 Y/移动/目标高度组合，以及 96/96 个跑跳、平滑转头、延迟观测组合完成投掷。包含 Height=25、Rotation Speed=180，和高于顶点的目标。最新完整回归中，独立种子的 79,872 次风弹散布模拟有 79,512 次命中，17,546 次处于目标 ±0.75 格；两者单独统计，不能把命中率称为高度精度或实服成功率。默认站立目标 25 格名义预测为 24.542 格，自动等待 8 tick。

### 偶发漏接与 Height=45 专项修正

实机日志证明两次 Height=45 的风弹都已提交，等待 14/17 tick，预测目的地仅为起点上方约 28.5 格。日志没有命中确认，不能把提交当作成功，也不能仅凭客户端模型断言服务器失败的全部原因。重新通过 Recaf 核对了 Lunar 珍珠重力/阻力、风弹匀速、扫掠碰撞和年龄扩张；未改动 jar。

旧选择目标的问题：高度误差的权重远高于接触余量；等待逻辑只要未来能更高一点就放弃当前窗口。在目标超过珍珠顶点时，这会持续选择接近顶点的时机，此时珍珠每 tick 扫掠高度变短，风弹飞行时间更长，随机散布和时间偏差更容易使两者错开。

早期修正将 ±0.75 格内的名义高度视为同等精度，再比较命中余量；在当时的 64 个随机探针之外增加 26 个散布边界探针，以及珍珠相位前后 1 tick 的名义探针。相位散布最初采样 32 次，20 格修正扩展到 128 次。当前重构进一步将名义探针扩展到 128 次，并增加本页顶部列出的相位可靠性硬门槛。等待时使用相同的综合代价，实际投掷按当前平滑/量化后的角度复验。静止目标 45 的标准模型等待 11 tick、预测约 26.904 格；不保证达到不可达的 45 格。

冻结上一版高度优先目标函数作为 A/B 基线，在相同珍珠状态、量化和门槛下比较：48 组 Height=45 场景都完成投掷；最新完整回归中，49,152 个独立风弹散布样本旧/新漏接 231/23 次，另加前后 1 tick 偏差的 98,304 次模拟旧/新漏接 5,829/1,243 次。相位偏差是压力测试假设，不是实测服务器偏差；这些结果不能换算成实服命中率。

### 20 格静止/移动专项

`TwentyBlocksTest.cpp` 使用两组独立种子、三档灵敏度、四个方向，以及静止/行走/疾跑/斜向/转向/急停/加速七类移动；包含延迟两个 tick 的珍珠快照和速度包 1/8000 量化。共 672 个触发场景必须全部发射风弹，每个移动桶、每个种子都用 49,152 个独立散布样本检查名义、提前/延后一 tick 三种相位。每个桶的 95% Wilson 下界必须大于 95%，不能用总平均掩盖单类移动失败。

旧版种子 2026092920 的疾跑提前一 tick 场景为 94.047%，名义为 99.589%。最差相位惩罚和高度达标后的可靠性比较修正后，同一桶分别为 99.658% / 100%。两组种子全部桶最低命中率为 99.296%。这不是实服成功率；测试中目标 20 的名义高度最大偏差约 3.79 格，命中统计不等同于精确 20 格。场景限定普通地面移动；跑跳另有旧回归，服务器修改弹道、严重网络抖动不在这一概率结论内。

投出后增加 `FlightObservation` 只读跟踪，不占用转头、物品栏或手动输入，不补投。通过所有者、排除已有实体和反推发射点来识别风弹，日志记录实际速度相对预测速度的差异；珍珠消失后观察附近传送，最多观察 90 tick。实体缺失、切世界、观测被下一次覆盖均不视为成功；`nearbyTeleport` 是间接观测，不是服务端碰撞确认。用它区分“提交使用”“风弹实际生成”“观察到附近传送”，避免把每次 API 返回成功当成已接住。

日志 `AutoCharge: start/pearl submitted/waiting/height plan/intercept/stop` 区分珍珠是否已提交、实体拟合、交互占用、角度/路径/散布等待以及结束原因。等待日志最多每 10 tick 一条；高度计划记录目标绝对 Y、预测 Y、误差、等待 tick 和飞行 tick；intercept 记录实际角度、平均余量、各类探针漏接计数和继承速度。灵敏度每游戏 tick 通过 JNI 读取一次，避免每个候选角度重复访问游戏对象。

## 与现有系统接入

- 模块放在 `src/minecraft/modules/player/autocharge/`，注册到现有 Registry / CMake / 配置和按键系统。
- 使用 `rotation::SetExclusiveRotations` / `OwnsExclusiveRotations` / `ReleaseExclusiveRotations`。沿用 AutoMLG 的按 tick 平滑及灵敏度修正，不添加独立转头管理器。
- 全程不调用摄像机转动接口；结束释放独占请求，由共享管理器把静默朝向归还实时摄像机朝向。保持已有连续 yaw 与手部插值修复。
- 移动修复直接使用用户实时摄像机 yaw；不再覆盖控制基准，不复制 FixMovement。
- 使用 `SetSilentSlot(this, slot)`、`SyncSelectedItem()`、`UseSilentItem(expected,yaw,pitch)` 和 `ReleaseSilentSlot(this)`。投掷时验证有效槽位，并让原生 useItem 构造携带角度、交互序号的包；不直接覆盖物理热栏选择。每次提交后保持有效槽位到 tick 结束，下一次 GameTick Pre 再恢复，避免 use → held-item-change 触发 PacketOrderE。取消及 JNI 返回失败也遵循该边界。
- 使用 GameTick / PrePlayerInteract 现有事件。Motion Post 不作为服务器确认；第二发使用当前受控朝向重新验证轨迹，不照搬 1.8 Scaffold 的确认假设。
- 补充 `KnownItem::WindCharge` 和支持版本的映射；添加可复用的投射物种类、所有者、速度、冷却查询。已有 WorldEntities / EntityById 可用于小范围发现和随后按 ID 跟踪，不把珍珠误当 LivingEntity 处理。
- ThrowableAura 当前入口限制 Legacy Lunar，不能直接拿它当现代风弹适配层；可参考其预测/遮挡设计。
- FreeCam 阻止启动。Scaffold、AutoMLG 正在工作时 AutoCharge 让路；取得租约后发布 IsWorking，让其他转头/投掷/背包整理模块显式避让。AutoMLG 紧急接管时先让 AutoCharge 取消，不能粗暴清除别人租约。
- AutoBlock 占用物品交互、Velocity/AntiKB 正在延迟或 Backtrack 正在缓存时，取消执行；不清空这些模块的队列。FreeLook、打开界面也会中止执行；手动使用键在执行期间被屏蔽。AutoMLG 确认紧急落水/灭火/解网位置后可要求 AutoCharge 归还资源；普通自动收水则等待 AutoCharge 完成。

## 首版设置

保持少量设置，不加第二种模式：

- `Rotation Speed`：复用本项目常用范围 1–180，默认 90；太慢而错过窗口时取消，不强制瞬转。
- `Height`：5–45 格，步进 0.5 格，默认 25；控制珍珠第一次碰撞并传送时的目标高度。
- 不再提供 `Restore View`：静默模式始终不改变用户视角。

疾跑补偿、珍珠跟踪、障碍检查和单次执行属于基础逻辑，默认启用，不再各加一个开关。使用现有通知报告缺少物品、等待冷却、无拦截窗口；不增加独立 HUD。
