# CS2 崩溃定位：2026-09-23

此记录包含 00:33、00:39 和 01:40 三次崩溃的诊断。崩溃诊断未修改正式源码或 DLL，未注入游戏；首次诊断使用本地独立子进程验证了反射加载器的异常处理。

## 结论

三次异常均为读取无效本地 Pawn 的 `cameraServices` 指针时，在 VCRUNTIME140 的 8 字节复制中触发访问异常。地址和渲染线程栈数据与新增 Aimbot 范围圈的 `CaptureVerticalProjection` 路径吻合。该路径先从全局取得 Pawn，立即读取 `Pawn+0x1240`，之后才执行完整相机/玩家/会话检查。

导致本应被跳过的读取升级为进程崩溃的关键缺陷：生产反射加载器没有注册 PE 的 x64 异常展开表。它复制节、导入和重定位后直接进入 DLL；源码中的 `__try/__except` 因而不能像普通 LoadLibrary 加载的测试程序一样可靠工作。

- 失败读取地址 = 本地 Pawn + `0x1240`，即本版 `cameraServices`。
- R13 = `client.dll + 0x23CCC08`，即本地 Pawn 全局；转储中该地址的值与上表 Pawn 完全一致。

- 栈下方含 DX11/Steam Overlay 呈现路径；前两份转储的前几个手动映射区返回地址具有相同布局。

这些小型转储没有包含 Nova 手动映射代码区，现存 MAP 文件也属于旧构建，因此不伪造完整 Nova 符号栈。故障数据地址可以精确核对；触发路径由该地址、寄存器/栈数据及当前源码交叉确定。具体是切图、退出对局还是重生导致 Pawn 失效，日志没有记录，尚不能判定。

## 01:40 再次崩溃

最新转储 `cs2.exe.35724.dmp` 于 01:40:20 写入，故障线程 50784。异常流的寄存器上下文（并非仅用线程列表推测）确认：

- RIP=`0x7FFED364C11D`，RDX=`0x437DF2D1240`，R8=`8`。
- client.dll 基址=`0x7FFDB0800000`；R13=`0x7FFDB2BCCC08`，正好为本地 Pawn 全局地址。
- 该全局存储 `0x437DF2D0000`；与失败读取地址之差仍为 `0x1240`，`RSP+0xD0` 也存有这个 Pawn。
- 栈中 `0x2CED876FD`、`0x2CED86EE6` 所属手动映射代码未包含在转储中，当前 MAP 也为旧构建，因此不声称得到完整、精确符号化的 Nova 调用栈。

最新 Nova 日志显示 PID 35724 曾完成正常卸载，再次初始化并于约 01:39:05 就绪，之后没有卸载/退出记录。Steam 01:40:23 记录进程退出码 `-1073741819`，即 `0xC0000005`。01:39:31 虽有服务器状态变化日志，但无法仅凭它确定失效 Pawn 是由切图、死亡还是其他状态转换导致。

诊断当时，相机读取在 `src/cs2/sdk/camera/Camera.cpp` 的 `CaptureVerticalProjection` 中，先读取 Pawn 的 cameraServices，再检查 IsLocalCamera。`src/core/ReflectiveLoader.c` 尚未调用 RtlAddFunctionTable。此前 FOV 行为修复和 Watermark 信息接入没有覆盖这两处缺陷；Watermark 新读取使用 ReadProcessMemory，且不访问 cameraServices，本次证据不指向 Watermark 数据采集。

## 独立复现

使用未修改的 `src/core/ReflectiveLoader.c` 和已有本地测试宿主，构建一个包含 `__try/__except` 的最小读取探针。源码和构建输出位于 `Client/build-vs2026/analysis/seh-probe/`。测试只在自己的进程里运行：

1. 不注册异常表：`RtlLookupFunctionEntry` 返回空；读取 PAGE_NOACCESS 页面后退出码 `-1073741819`（0xC0000005）。
2. 唯一关键差异为注册该映像的异常表：函数条目可查；相同读取被 `__except` 捕获，返回预期 42，进程退出码 0。

原来的 smoke 在普通加载的 EXE 中执行，覆盖了逻辑和 Hook，却没有覆盖反射映射后的 SEH；因此先前通过 smoke 不能排除这一加载器缺陷。

## 修复方向

1. 映像完成导入与重定位后、执行 DLL 入口之前注册 x64 异常表；注册失败时终止启动并报告错误。
2. 卸载排空所有回调，释放映像前移除对应函数表，避免函数表指向已释放内存。
3. 范围圈采集先验证连接、本地 controller/Pawn 完整句柄和生命状态，再读取相机服务；采集失败即跳过绘制。
4. 增加生产反射加载方式下的访问异常捕获与卸载回归，不只测试普通 EXE 路径。

以上为诊断时的修复建议；下述修复现已实施，并重新构建正式 DLL。

## 修复实施与离线验证（2026-09-23）

### 相机读取

`Camera.cpp` 将本地相机验证合并到同一读取流程：先确认连接状态、实体系统、controller/Pawn 完整句柄、实体反向身份、生命状态和队伍，再读取 `cameraServices` 及其 owner。范围圈不再提前解引用旧的 Pawn。矩阵读取后再次验证本地玩家、相机与连接，失败时投影输出保持 0，跳过本帧绘制。

相机读取使用 `ReadProcessMemory` 并校验完整读取字节数；即使对象在校验与读取之间被销毁，也通过失败返回跳过，不依赖本地 memcpy 引发异常来判断地址是否有效。

### 反射加载与卸载

`ReflectiveLoader.c` 在导入和重定位之后、进入 CRT/DLL 入口之前调用 `RtlAddFunctionTable`。`UnwindTable.h` 验证异常目录边界、条目尺寸、函数范围和排序。无法解析 API、元数据无效或注册失败时报告失败并终止启动；入口返回 FALSE 时移除已注册函数表后释放映像。

反射入口仍保持无 CRT、无静态字符串依赖。Bootstrap 的 `Loader error N` 含义：1 为系统 API 解析失败，2 为映像分配失败，3 为异常目录无效，4 为函数表注册失败，5 为 DLL 入口拒绝启动。

宿主原有回调排空之后，`SelfUnload.cpp` 在映像外的卸载代码中先调用 `RtlDeleteFunctionTable`，成功后才释放映像并退出线程。删除失败时保留惰性映像，避免 Windows 引用已释放的函数表。普通 `LoadLibrary` 映像继续交由 `FreeLibrary` 管理，不手动删除其异常表。

### 验证边界

本轮未注入游戏。切图、重生、退出对局和重新注入等真实场景，需要使用新 DLL 进一步观察，离线通过不等于已证明所有游戏崩溃均消失。

额外探索的 MSVC C++ `throw/catch` 探针仍以 `0xE06D7363` 退出；本次注册验证证明的是 Windows SEH（`__try/__except/__finally`）恢复正常，不声称完整解决反射映像的 C++ 语言异常兼容性。该额外限制的具体原因尚未分析，不属于三份转储中已确认的 `0xC0000005` 读取异常。
