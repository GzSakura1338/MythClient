# LegitAnchorAura 设计

状态：已实施原生 C++/JNI 模块，支持 Lunar 1.21.11 和 Minecraft 26.3。实际行为、验证命令及适配差异见 `legitanchoraura.md`；下文保留设计背景。

持续开启后，在合法范围内自动选择玩家和重生锚位置，执行放置、一次充能、引爆，再继续下一轮。设置布局参考 LegitCrystalAura，使用现有 C++/JNI、RotationManager、移动修复、物品交互事务、槽位管理和 ImGui ESP。

| `AnchorAuraData.getAnchorAuraData2056` | 比较目标伤害 | 同阶段比较目标伤害，接近时保持已有位置，减少转头抖动 |

参考代码的 `is2875` 明确标注反编译不完整；`do2868` 实际交互固定 MAIN_HAND，而参数 hand 用于挥手，不能把调用参数 OFF_HAND 直接理解为副手引爆。实施前须用实际支持版本的原版交互分支校验充能和引爆条件。

不移植 Mio 的本地强制改空气（inhibit）、网络回调内立即补放、异步读世界、空气放置、液体特殊放置和独立颜色/淡出参数。采用本项目真实世界确认和主题渲染。

## 参数

模块名称：`LegitAnchorAura`，分类：Combat。保持现有 Enabled、Bind、隐藏 ArrayList 等通用设置。

| 设置 | 默认 | 范围及说明 |
|---|---|---|
| Target ⚙ → Range | 4.5 | 1–6，步长 0.1；实际操作还受原版交互距离限制 |
| Target ⚙ → FOV | 180° | 1–360°，步长 1；按玩家视角筛选目标 |
| Target ⚙ → Through Walls | 关 | 忽略世界方块遮挡；仍必须命中选定方块/支撑面并满足距离 |
| Place | 开 | 允许新放锚；关闭后仍能处理已有合法锚 |
| Place ⚙ → Delay | 0 ms | 0–1000，步长 5；连续新放锚的最小间隔 |
| Place ⚙ → Auto Switch | 开 | 自动从快捷栏选锚、萤石和可引爆物品 |
| Place ⚙ → Silent | 关 | 复用已有 slot spoof，保持本地手持显示；作用于三个阶段 |
| Detonate | 开 | 自动充能并引爆；关闭时仅放置，不消耗萤石 |
| Detonate ⚙ → Delay | 0 ms | 0–1000，步长 5；连续引爆的最小间隔 |
| Swing | 开 | 控制本地挥手，必要的网络挥手仍遵循已有交互规则 |
| Rotation ⚙ → Speed | 45°/tick | 1–180，步长 1；始终静默转头并使用移动修复 |
| Safety ⚙ → Ignore Self Damage | 关 | 跳过自身伤害限制，仍保护队友 |
| Safety ⚙ → Min Target Damage | 4 | 0–36，步长 0.5 |
| Safety ⚙ → Max Self Damage | 6 | 0–36，步长 0.5 |
| Safety ⚙ → Min Remaining Health | 4 | 1–20，步长 0.5；生命与吸收值合计 |
| Place ESP | 开 | 显示当前操作的锚方块，使用现有 HUD 主题色 |

不增加充能次数、独立充能 Delay、预测 tick、强制面、空放、线程、重试次数等设置。只充一次就足够引爆；这些由内部状态机处理。Auto Switch/Silent 虽位于 Place 齿轮内，但统一作用于全流程。关闭 Auto Switch 时，仅使用当前有效手持槽能完成的动作，不偷偷切槽。

不机械复制 Only Above Crystal：锚使用方块中心作为爆炸源，按实际伤害、遮挡与安全限制筛选；Y 轴不是唯一判定依据。

## 工作流程

`选位 → 放置 → 确认锚出现 → 充能 → 确认 CHARGES > 0 → 引爆 → 确认锚消失 → 重新选位`

1. 收集 Range/FOV 内合法玩家，排除自己、死亡、旁观、Teams 队友和 AntiBot 对象。
2. 优先使用安全、可交互且达到最低伤害的已有锚。已充能直接进入引爆；未充能且有萤石进入充能。多个已有锚先比较可执行阶段，再比较伤害，避免无材料候选占住任务。
3. 无有效已有锚时，Place 开启且快捷栏有锚才搜索新放位置。完整攻击模式还要求有萤石和可用引爆槽，避免放完后卡住；仅放置模式不要求这两种物品。
4. 新位置必须可放、无实体占位、有合法邻接支撑、在世界高度与边界内。处理可见命中面和距离后，再做昂贵的伤害计算。
5. 使用真实方块状态推进阶段。默认每 tick 最多提交一次方块交互，Delay=0 也不在同 tick 连发放置、充能和引爆。
6. CHARGES 已大于 0 时不重复补萤石。引爆前选非萤石且不会被物品使用逻辑抢占的主手槽，优先原持槽或空槽；双手物品都需检查，避免主手为空、副手萤石时发生额外充能。具体可用手/槽由原版机制校验决定；无合法组合则暂停，不丢弃或移动用户物品。
7. 读到锚消失才开启下一轮。原生调用返回成功不等于服务器确认，提交已进入但结果不明时也进入等待，避免重复交互。
8. 确认超时后重新读取方块状态与材料，再决定重试或换位；失败位置短暂冷却，防止重复点击同一被拒位置。

每个动作前重新检查目标、当前维度、距离、伤害、材料、命中面和交互所有权。目标离开或安全条件变化时不继续充能/引爆，不自动拆除已经放出的锚。

## 位置与伤害

采用 Mio 的“已有锚优先、新位置伤害最大”思路。每个位置取合法目标中的最高有效伤害，队友和自身检查始终独立执行。目标伤害相近时复用当前位置；已经提交的阶段在确认期间固定，不因另一位置的小幅提升打断。

爆炸中心为锚方块中心，强度 5、基础伤害作用半径 10。不能直接调用写死强度 6、半径 12 的水晶伤害函数。实施时提取可传入爆炸强度的公共公式，水晶仍传入 6，并保留其原测试结果。

参考 Mio 计算已有锚伤害时忽略将被引爆的锚自身遮挡，避免把它错误当作保护墙；新锚也不能作为永久阻挡物参与本次爆炸的遮挡计算。该忽略只作用于曝光采样，不改动真实世界。原版水保护等锚特有分支须在支持版本中确认并纳入适配，读取失败则不执行。

目标移动使用已有短期碰撞预判，按剩余放置/充能/引爆步骤估算时长；提交前用当前状态复检。当前和预测自身安全都必须通过。保留队友保护，不承诺预判能覆盖玩家未来输入或服务端特殊伤害规则。

扫描在游戏线程分批执行：以当前水晶的 128 网格访问、2 个详细候选和 2 ms 软预算为起点。多目标伤害查询另设内部预算，未完成的候选跨 tick 继续，不能让“每候选遍历全部玩家”绕过预算。缓存仅保存数据快照、实体标识和世界标识，执行前重新解析，不跨线程持有临时 JNI 引用。

## 与现有模块协作

- 复用 RotationManager 静默平滑转头、灵敏度处理与移动修复。准备在 GameTick，提交在现有 PrePlayerInteract 事务阶段；不直接改摄像机视角或额外发送旋转包。
- 保留现有紧急模块优先级。自救、物品使用冲突和延迟发包期间暂停，暂停后重新检查状态，不继续旧角度/旧槽位任务。
- 与 KillAura 同水晶模块一样：只有已找到可执行计划并取得转头所有权时占用。KillAura 通过统一爆炸交互工作状态让位，搜索空转时不阻止普通攻击。
- AnchorAura 和 CrystalAura 共用一个轻量交互协调器，避免仅依赖订阅先后而互相抢转头。已提交的确认阶段优先完成；均空闲时按有效计划目标伤害选择，接近时保留上个拥有者。只有真正可执行的计划可竞选，缺物品或尚未搜索完成不得占用。双方的扫描预算也应有合计上限。
- 连续工作时保持槽位会话，按锚→萤石→引爆物品切换，不经过原槽。停止、禁用、失去目标后恢复；用户手动滚轮、原物品替换、其他模块占槽、恢复同步失败均遵循现有恢复规则。
- 方块更新回调只记录状态，不直接调用放置或使用物品。换世界、重生、熔断时清除任务和 ESP，释放所有权。

## 文件与复用边界

新增 `Client/src/minecraft/modules/combat/legitanchoraura/`，集中放置模块入口、锚状态机及规则。新增 `java/api/game_anchor.h` 与 `java/game/GameAnchor.cpp` 作为原生 JNI 适配，沿用项目路径惯例；不编写 Java。

将确实需要共用的爆炸伤害参数、曝光采样、移动预测、方块命中及放置 ESP 抽到 combat 公共组件，水晶和锚分别传入规则。避免复制整份 LegitCrystalAura，也避免为本次功能全面重构无关模块。新模块通过现有 Registry、属性、配置和快捷键系统接入。

需补齐的映射/原生能力：锚物品与萤石识别、锚方块与 CHARGES 属性读取、维度 respawnAnchorWorks、合法放置状态、主副手使用分支、爆炸曝光忽略当前锚及水保护处理。首期对齐目前水晶模块支持的 Lunar 1.21.11 和 Minecraft 26.3；其他版本能力不足时明确提示并关闭，不能使用猜测映射。

## 实施顺序与验收

1. 通过实际支持版本原版代码确认锚交互、维度和爆炸机制；校验所需映射。
2. 提取少量公共组件，先验证水晶模块行为不回退。
3. 实现锚放置、充能、引爆和世界确认状态机，再接入简洁设置与 ESP。
4. 加入两种爆炸模块的共享调度及 KillAura 让位。
5. 原生模拟回归通过后构建 DLL，再进行实机测试。

测试必须覆盖：完整循环、已充能直接引爆、未充能只充一次、无材料、主副手萤石、引爆槽选择、延迟/失败/乱序方块确认、移动中目标离开、墙体与距离限制、实体占位、自伤与队友保护、特殊维度、恢复原槽、Silent/Swing、手动滚轮、紧急模块接管、锚与水晶同时启用及 KillAura 同时工作。性能测试覆盖多个目标与密集候选，统计整 tick 的 JNI/曝光预算。

设计对齐 Mio 的核心操作与选位方式，保留本项目安全条件、确认机制和输入管理；不将其称为 Mio 全部行为的一比一复制。
