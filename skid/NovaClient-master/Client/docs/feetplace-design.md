# FeetPlace 自动围脚设计

状态：首版已实现，待实机验收。模块命名 `FeetPlace`，放在 Combat。开启后用快捷栏黑曜石围住玩家脚部，完成后保持监测，缺口出现时继续补放。以下保留设计依据，实际首版差异见文末。

## Mio 源码结论

阅读来源：

- `skid/OpenMio-main/src/main/java/me/mioclient/module/combat/FeetPlace.java`：`getList877` 候选生成和递归扩展，`getList1401` 四侧与下方偏移，`getComparator1402` 排序，`do1405` 居中，`onChunkDeltaUpdate` 更新触发。
- `skid/OpenMio-main/src/main/java/me/mioclient/module/Delay.java`：继承的放置、物品选择、延迟、转头、实体检查和自动关闭逻辑。
- `skid/OpenMio-main/src/main/java/me/mioclient/HoleSnapSearchHelper4.java`：脚部位置采用 X/Z 向下取整、Y 四舍五入；包围盒四角推导跨格占位及外圈。
- `skid/OpenMio-main/src/main/java/me/mioclient/PhaseESPSearchHelper4_2.java`：支撑面、最多两格辅助位置搜索、可替换和实体占位检查。

Mio 的核心并非固定在坐标四周放四块：它检查脚部四侧和下方，当候选与生物相交时递归扩展；没有可交互支撑面则寻找辅助位置。正常情况下按转头角度排序，高速移动时参考运动方向，部分碰撞场景改用距离排序。Sequential 会在方块更新时再次触发处理。

其父类 Delay 默认 50 ms、BPT 8；优先黑曜石，也有高爆炸抗性方块备选。FeetPlace 有 OnlyObby、Center、Flatten、Sequential 字段，但设置由 `Loader.settings` 初始化，不能从这些文件确认其默认值。反编译结果还含若干空条件分支，因此 Flatten 等细节不能宣称已经完整还原。

## 本项目的行为

1. **确定围脚区域。** 以玩家当前脚部包围盒推导所占格子，去掉边界浮点误差，生成外圈四邻接位置并去重。站在单格中央通常四侧各一块；跨格站立扩大到实际占位外圈，不向身体内放方块。完整固体已封住的位置直接视为完成，不挖掉替换。
2. **处理脚下与支撑。** 检查脚底必要支撑及各围脚位置的真实邻接面。可直接放置时优先填缺口；否则只为该缺口寻找最多两块辅助支撑，按依赖先后放置。辅助路径必须逐步相邻，每一步可达、可交互且不与实体碰撞，不能把 Mio 的“两格搜索结果”误当成已经连通的路径。
3. **有限扩展。** 玩家跨格或相邻生物占用候选时参考 Mio 向外扩展，但限定在玩家附近和实际交互距离内；每次规划最多 32 个候选，使用坐标去重，不能沿人群无限递归。扩展到上限仍无法形成合法围脚区域时保留可执行部分，等待环境变化。
4. **稳定顺序。** 先保留已经选定且仍有效的当前动作。新动作在依赖满足后按需要转头的角度排序、距离作为次排序、方块坐标作为稳定平局规则。首版采用这一确定性顺序；Mio 的高速运动方向分支不直接照搬到原地防御模块。
5. **持续维护。** 围完后释放转头和槽位，低频检查外圈。收到附近方块变化时标记需要重算，在下一次游戏 tick 处理，网络回调中不直接转头或放置。服务器位置修正、重生及世界切换清空旧计划，禁止对旧坐标继续放置。
6. **离开处理。** 默认跳跃或离开当前围脚占位区域时自动关闭。关闭 Auto Disable 后，在空中暂停新放置，落地后重新围住当前位置；不会在持续走动时铺出黑曜石道路。骑乘、死亡、FreeCam、打开界面期间暂停并释放控制。

不强制修改玩家坐标居中，首版只用黑曜石，不补头顶、不自动挖掘、不自动攻击挡路水晶。挡路实体消失后重试。这些是本项目的精简选择，不是对 Mio 原版全部选项的一比一复刻。

## 设置布局

沿用本项目模块开关、快捷键及小齿轮样式，不增加独立界面。

| 设置 | 建议默认 | 行为 |
|---|---|---|
| Place Delay | 50 ms | 0–250 ms，步长 5；两次实际提交之间的最小间隔 |
| Silent | 开 | 复用槽位 spoof；关闭则正常切换手持槽位 |
| Swing | 关 | 控制本地挥手；仍保留交互所需的挥手包 |
| Rotation → Speed | 45°/tick | 静默平滑转头，范围 1–180 |
| Auto Disable | 开 | 跳跃或离开围脚区域后关闭模块 |
| Place ESP | 开 | 显示当前计划放置块，复用现有 ImGui 方块 ESP、主题颜色与淡出 |

自动切黑曜石、完成后恢复原槽固定启用。无黑曜石时释放控制、限频提示并等待补充，不自动整理背包。交互距离自动取游戏实际值，不增加 Range、BPT、AirPlace、StrictDirection 等设置。

## 放置状态机与模块协调

流程：`检查环境 → 生成/更新外圈 → 选取可执行动作 → 平滑转头 → 实际射线复检 → 获取槽位 → 提交一次放置 → 等待结果 → 下一缺口/完成监测`。

复用 `RotationManager` 的独占转头、移动修复、交互角度锁定和 `PlacementTurnGate`。即使 Delay 为 0，也最多每 tick 一次自动交互；移动包提交后不再启动新动作。继承当前“角度一致”和重复大幅转头变化保护，不自行发送额外移动包。

复用 `HotbarSession` 的连续切槽及恢复逻辑。只在真实射线命中所需支撑面后切槽；有连续动作时保持槽位，完成、暂停、禁用后恢复。用户手动滚轮、物品身份变化、其他模块取得所有权时不能被旧恢复操作覆盖。

提交后等待客户端目标方块状态变化；客户端预测不等同于服务端确认。等待有超时，建议初始 300 ms，超时后失败位置冷却 500 ms 并重算，禁止每 tick 对同一未确认位置重复发包。方块之后被服务端撤销时重新识别缺口。只有实际世界里已存在且可交互的支撑才能解锁下一步。

优先级建议：现有自救、已开始的 AutoMace/AutoMLG/AutoCharge 事务优先，FeetPlace 暂停；Scaffold 工作时 FeetPlace 暂停。存在可执行围脚缺口时，FeetPlace 优先于普通 KillAura、自动水晶和重生锚；完成或等待失败冷却时释放优先权。已经提交的其他模块事务不可被抢占。

实施时需接入水晶和锚的规划仲裁阶段，而不是仅依靠 Tick 回调先后顺序抢独占转头。一次获得优先权后再进行切槽和交互，避免两模块同 tick 分别用不同物品、不同角度。围脚未工作时不影响其他模块。

## 代码结构与版本适配

- `Client/src/minecraft/modules/combat/feetplace/FeetPlace.cpp`：设置、状态机、事件和所有权。
- 同目录 `PlacementPlan.h`：小型原生几何规划，负责包围盒外圈、去重、支撑依赖及稳定排序，便于无需游戏的测试。
- `Client/src/minecraft/java/api/game_blockplace.h`、`java/game/GameBlockPlace.cpp`：通用方块放置适配，读取所持黑曜石、实际碰撞形状、世界边界、实体占位并调用原版控制器。
- 复用现有 `BlockAim`、`HotbarSession`、`PlacementTurnGate`、ImGui 放置 ESP。公共能力可以改为中性的命名空间，保留兼容入口，避免顺带重写水晶或锚逻辑。

不能直接使用 `PlaceCrystalBase`：其 `CrystalBaseBuildable` 额外检查上方空气和水晶占位空间，会误拒绝合法围脚方块。应复用底层 JNI、射线及事务机制，独立检查黑曜石本身的真实放置体积。

首批适配目标为当前锚/水晶使用的 Lunar 1.21.11 和 Minecraft 26.3。围脚本身不依赖现代物品，规划保持版本无关；其他受支持版本需要补验对应控制器、碰撞及事务入口后启用，不能直接套用现代版本绑定并标注支持。全程 C++/JNI，不新增 Java 源码或字节码。

## 实施与验收

1. 实现纯几何规划并测试单格、跨两格、四格交界、半砖/台阶、实体阻挡、缺支撑、两级支撑依赖、循环去重和候选上限。
2. 实现通用放置边界，校验两版本 JNI 绑定；验证上方不是空气时仍能合法围脚，身体占用时绝不放置。
3. 接入状态机、槽位、转头及模块仲裁。测试连续围脚、补缺口、Delay=0 仍单次提交、超时、服务端撤销、缺材料、手动切槽、禁用恢复和世界变化。
4. 接入设置和 ESP，测试 Silent/Swing 的组合以及工作结束时的恢复。
5. 构建 DLL 后实机验证：原地完成围脚、跨格不夹身、破坏一块后补回、跳跃/离开关闭，以及与 KillAura、水晶、锚、自救模块同时开启时无重复提交或遗留槽位/转头所有权。

模拟和构建可证明原生规划与状态机的受测行为；放置接受率、服务端修正和实际网络时序仍需要实机验证，不承诺仅凭阅读代码即可保证所有服务器表现一致。

## 首版实现说明

- 已接入模块注册、配置、设置 UI、ImGui 放置 ESP、Silent/Swing、延迟、平滑转头、移动修复、自动关闭和槽位恢复。支持 Lunar 1.21.11 / Minecraft 26.3，其他版本启用时提示并关闭。
- 规划和纯几何代码集中在 `modules/combat/feetplace/`。通用黑曜石放置使用 `GameBlockPlace.cpp`，复用锚已有的全立方体占位检查；没有使用水晶专用的上方空间限制，也不调用锚的伤害或维度爆炸判断。
- 单次外围规划最多 32 格，每 tick 搜索最多 48 次候选检查，在目标之间检查 2 ms 软预算。单个 JNI 调用和辅助支撑链不能承诺硬性 2 ms 完成。
- 完成后的缺口每 100 ms 轮询检测；首版尚未接入方块更新事件触发。世界/玩家变化和 Respawn 会清除旧计划，单独位置修正后的下次 tick 按实际占位处理，默认离开占位自动关闭。
- 已提交的水晶/锚确认流程优先。FeetPlace 在自救 tick 处理后申请独占转头；实际有围脚动作时暂停普通水晶/锚和 KillAura。空中暂停，即使关闭 Auto Disable 也不进行空中围脚。
- ESP 直接复用现有 `PlacementEsp` 的主题渲染和过期处理，首版没有独立新增淡出动画或 Surround 搜索别名。
- 原生回归：`Client/test/combat/feetplace/run.ps1`；覆盖几何、支撑依赖、完整围脚/补回、逐 tick 提交、延迟、切槽及恢复、手动滚轮、跳跃/离开、缺材料、骑乘、自救、同 tick 紧急接管、确认超时、Swing、同步失败和爆炸模块仲裁。共享受影响行为另跑水晶、锚及 KillAura 回归。
- 映射核验：`Client/test/combat/legitcrystalaura/mapping.ps1 -Adapter GameBlockPlace.cpp -Macro NOVA_NO_EXTRA -OutputName test-blockplace-mapping`，现有两个 jar 的 19 个命名 JNI 绑定通过；睡眠检查另复用现有 LivingEntity.isSleeping 绑定。
